# ADR 0007: Managed Caddy ingress and verified custom domains

Status: Accepted

## Context

Rundea workloads bind only to loopback host ports on their selected node. A public URL therefore needs a separate ingress layer that can terminate TLS, route hostnames to the correct local workload, survive redeploys, and remain portable across arbitrary Linux VPS providers.

Installing and maintaining a distro-specific host web server would weaken BYOVPS portability. Exposing workload containers directly on public interfaces would weaken isolation and make automatic HTTPS/domain lifecycle harder to reason about.

## Decision: one managed Caddy runtime per node

The Agent owns one `rundea-caddy` Docker container per node. It runs with host networking so its upstreams can remain `127.0.0.1:<managed host port>`. Caddy configuration is generated deterministically from the full desired route set, written atomically, validated before apply, and reloaded for normal changes.

The Caddy image is pinned by version and multi-platform digest for a given Rundea release. `/data` and `/config` persist outside the container so ACME state survives container replacement.

Workload containers are not made public by this feature. Caddy is the only public HTTP/HTTPS ingress runtime.

## Decision: desired state, not incremental patches

The Control Plane sends the Agent the complete desired route set for a node on every reconciliation. The Agent does not receive "add this host" or "remove this host" mutations. This makes reconnects and retries idempotent and allows a node to converge from unknown local state back to PostgreSQL source-of-truth state.

Each reconciliation has a UUID. Domain rows participating in the operation carry that reconciliation ownership until the Agent result is accepted. Results from an old reconciliation are rejected.

A domain can be:

`PENDING -> CONFIGURING -> ACTIVE | FAILED`

Deletion is explicit:

`ACTIVE|FAILED|PENDING -> DELETING -> row removed only after successful Agent reconciliation`

This prevents the Control Plane from forgetting a domain while a stale Caddy route may still exist on the node.

Global reconciliation history is stored separately from domain rows so an empty desired route set can still report a failed Caddy cleanup.

## Decision: READY deployment ownership

A route is emitted only when its service has a `READY` deployment on the same node. A domain without a READY upstream stays `PENDING` with a diagnostic reason.

If a later READY deployment moves a service to another node, non-deleting domains move with that service. The old node is reconciled first to remove the old route, then the new node receives the new desired route set.

## Decision: what ACTIVE means

A local Caddy reload is not enough to mark a domain ACTIVE. The Agent verifies the public hostname through DNS and HTTPS.

For every reconciliation, Caddy injects an `X-Rundea-Reconciliation` response marker containing the current reconciliation UUID. The Agent resolves the hostname, discards private, loopback, link-local, multicast, CGNAT and benchmark addresses, pins the HTTP dial to the resulting public addresses, performs a TLS-validated HTTPS request for the hostname, and requires the response marker to match the current reconciliation.

This avoids two false positives:

1. the domain still points at an old provider such as Railway but happens to return valid HTTPS;
2. DNS is manipulated to make the Agent probe an internal/private address.

`ACTIVE` therefore means that a valid public TLS endpoint for the hostname returned the marker generated by the current Rundea Caddy configuration and did not return a 5xx response.

## Security boundary

The Control Plane does not perform arbitrary HTTP fetches to user-supplied hostnames. This avoids turning the Control Plane into an SSRF primitive.

The Agent only receives hostname -> local managed host-port routes. It cannot be instructed by this protocol to reverse proxy to an arbitrary remote upstream.

Wildcard domains are not supported in v0.

The node operator remains inside the workload trust boundary: root/Docker access can inspect or alter local runtime and ingress state.

## Consequences

This design gives Rundea provider-independent custom-domain HTTPS without Kubernetes or a host-specific package manager. DNS must point to the selected VPS and ports 80/443 must be reachable for ACME/public ingress to work.

Rollback/restart controls, GitHub App private-source delivery, node public-address discovery, and the first live Sendina migration remain separate slices.
